# 뉴스 목록 뒤로 가기 스크롤 복원 — 원인과 수정

**Status:** fixed (2026-11-22), 커밋 `fix: restore the scroll position when coming back to the news list`. push 전.
**관련:** [[2026-11-22-news-list-reading]] (실행 결과의 "눈에 띈 것"에서 넘어온 문제)

## 증상

- 뉴스 목록에서 아래로 내려가 기사를 열었다가 뒤로 오면 목록이 맨 위에서 다시 시작한다.
- 목록 개선 작업 전부터 운영 사이트에 있던 문제다. 홈·용어집·블로그·제품 목록은 정상이었다.

## 이 사이트의 스크롤 복원이 동작하는 방식

- 뒤로/앞으로 가기는 항상 **페이지 새로 고침**이다. `MainLayout.astro`가 `popstate`에서 `location.reload()`를 부른다(SSR 페이지를 제자리에서 바꿔 끼우는 것이 불안정해서 의도적으로 넣은 것).
- 새로 고침된 문서에서 Astro 라우터가 `history.state`에 저장해 둔 `{index, scrollX, scrollY}`로 스크롤한다.
- 라우터는 스크롤이 끝날 때마다 위치를 `history.state`에 저장한다. **단, `history.state`가 있을 때만** 저장한다.

## 원인 세 가지 (각각 증거로 확인)

### 1. URL을 고쳐 쓰는 스크립트가 state를 지웠다

- `NewsprintCategoryFilter`가 초기화할 때마다 `history.replaceState(null, …)`을 불렀다. 목록 검색(`newsListSearch.ts`)과 기사 안 찾기(`articleFind.ts`)도 입력할 때 같은 호출을 했다.
- 증거: 운영 목록에서 로드 직후 `history.state`가 `null`, 2000까지 스크롤한 뒤에도 `null`. 같은 조건의 홈은 `{index:0, scrollX:0, scrollY:276}`으로 저장되고 뒤로 왔을 때 276으로 복원됐다.
- 가설 검증: 운영 사이트를 그대로 두고 브라우저에서 "null이면 기존 state 유지"만 적용했더니 2000 → 2000으로 복원됐다.
- 수정: 세 곳 모두 `history.replaceState(history.state, '', url)`. `productCatalog.ts`가 이미 쓰던 방식이다.

### 2. 뒤로 가기를 두 장치가 동시에 처리했다

- 레이아웃의 새로 고침과 Astro 라우터의 뒤로 가기 처리가 같은 `popstate`에서 함께 돌았다. 라우터의 결과는 새로 고침으로 항상 버려진다.
- 라우터가 먼저 끝나면 문제가 된다. 라우터는 서버가 준 목록(항상 "전체 탭, 접힌 상태")을 제자리에 끼우고 저장 위치로 스크롤한다. 탭·검색 상태에서 깊이 내려가 있었다면 그 목록이 더 짧아 위치가 잘리고, 스크롤이 끝나면 **잘린 값이 저장값을 덮어쓴다.** 그 뒤에 새로 고침이 일어나 망가진 값을 복원한다.
- 증거(로컬, 리서치 탭 3000): 뒤로 가기 +1ms 라우터 시작 → +564ms 제자리 교체 후 3000 요청이 2297에서 잘림 → +602ms 저장값이 2073으로 바뀜 → +934ms 문서 종료.
- 운영에서는 새로 고침이 먼저 끝난다(홈 기준 뒤로 가기 +41ms에 문서 종료). 즉 응답 속도에 따라 결과가 달라지는 경주였다. 1번을 고치기 전에는 목록의 state가 `null`이라 라우터가 가만히 있었고, 1번을 고치자 목록에서도 이 충돌이 드러났다.
- 수정: 레이아웃의 `popstate` 처리기가 `event.stopImmediatePropagation()`으로 라우터의 처리기를 막는다. 레이아웃의 처리기가 먼저 등록되므로 먼저 실행된다. 라우터가 없는 관리자 화면에서는 막지 않는다(관리자 편집기의 자체 `popstate` 처리 유지).

### 3. 복원이 목록의 최종 모양보다 먼저 일어났다

- 새로 고침된 문서에서도 서버는 "전체 탭, 접힌 상태"를 준다. 라우터가 그 모양에 대고 복원한 직후에 탭·검색 스크립트가 목록을 바꾼다. 위치가 밀리고, 잘린 값이 다시 저장되기도 한다.
- 증거(검색 "Gemini" 1200): 1번만 고친 상태에서 뒤로 온 위치가 528.
- 수정
  - `NewsDeskList`의 인라인 스크립트가 페이지 해석 시점(라우터보다 먼저)에 저장 위치를 `window.__newsListScrollY`에 확보한다.
  - `newsDeskMode.ts`가 목록이 정리될 때마다(`update()` 끝) 그 위치를 다시 적용한다. 로드 후 2초 동안만이고, 사용자가 휠·터치·키·포인터를 쓰면 즉시 그만둔다.

재현 스크립트(Playwright, 로컬 개발 서버): 스크롤 → 링크 클릭 → 뒤로 가기 → 위치와 "화면 맨 위 기사"를 비교.

- 레이아웃을 바꿨으므로 다른 페이지도 확인했다: 홈, 용어집 목록, 블로그 목록, 제품 목록, 모바일 크기의 뉴스 목록, 기사 페이지. 뒤로 → 앞으로 → 다시 뒤로 모두 원래 위치다.
- 같은 페이지 안 점프(제품 목록의 `#cat-video`) 후 뒤로 가기는 수정 전(운영)과 수정 후(로컬)가 같다.
- 가드 테스트 `frontend/tests/history-state-preserved.test.cjs`: 공개 페이지 소스에 `history.replaceState(null` 금지(관리자 제외), 레이아웃 처리기의 전파 차단, 목록의 확보·재적용 코드.
- 전체 테스트의 실패 목록은 기존 16개 그대로, 빌드 오류 0.

## 확인하지 못한 것

- 운영 빌드에서의 최종 동작. 개발 서버에서만 재현·확인했다. 배포 후 같은 스크립트를 운영 주소로 돌려 확인한다.
- 관리자 화면. 로그인이 필요하다. 라우터가 없는 페이지에서는 전파를 막지 않으므로 코드상 변화가 없다.
- Safari·Firefox. Chromium으로만 확인했다.

## 남은 것 (이번에 고치지 않음)

- `pages/settings/index.astro`가 온보딩을 마칠 때 `history.replaceState({}, '', '/settings/')`를 부른다. state가 `{}`가 되어 `index`와 스크롤 값이 없어진다. 같은 종류의 실수지만 다른 페이지, 다른 흐름이다.
- 기사 안 찾기 입력창(`.newsprint-article-find`)은 모든 화면 크기에서 `display: none`이다. 사용자가 입력할 방법이 없다(`?q=`로 들어왔을 때의 강조 표시만 동작).
- `NewsprintCategoryFilter`와 `newsDeskMode.ts`는 초기화할 때마다 `window`에 리스너를 더한다. 페이지 전환을 거듭하면 중복된다. 동작에는 지장이 없다.

## 조사하면서 알게 된 것

- Playwright의 `page.goBack()`은 이 사이트에서 끝나지 않을 수 있다. 뒤로 가기 직후 새로 고침이 이어져서 대기 조건이 채워지지 않는다. `history.back()`을 실행하고 주소와 `readyState`를 폴링하는 방식으로 바꿨다. `page.evaluate`에는 기본 제한 시간이 없으므로 직접 걸어야 한다.
